## Design and boundary

`RuntimeGuard.register_scoped_service_files` is a new fixed explicit local entry point. It reproduces the current scoped sample, matches all three preview pins, verifies the selected actual artifact's fingerprint, re-resolves the saved plan and fresh Scout review after the artifact read, and validates source/requirements/plan scope before transactional registration. It retains the exact bounded fresh review including normalized declaration, catalogue, title assessment, observation/profile context, blockers, timestamp and both review/assessment digests. No source/artifact bytes or file paths are stored. The stored historical review does not need today's changing catalogue to validate. Local digests establish consistency, not independent authenticity or data permission.

The existing SQLite obligation payload has one optional versioned `scout_review` member. Its entire contents participate in the immutable registration digest and hence subsequent evidence-note chain and simulated invoice's obligation-head pin. The existing obligation ID is **unchanged** (same canonical artifact binding); there is no new table, separate competing ledger, rewrite of older registrations or duplicate scoped obligation for the same artifact. Re-registration of the same stable scope returns the original record even if time advances. A different scope or an existing legacy record without provenance blocks scoped registration. Legacy registration of an already-scoped record returns that intact record; no provenance is stripped. Existing v1 records remain readable; older binaries may reject new scoped payloads, so do not downgrade without preserving a verified backup. Existing backup includes the same database. Historical read validation and native obligation history show the scope and review time; a new native registration button and dedicated recovery drill remain outstanding.

No external authority, real acceptance, invoicing, collection or payment. Cross-file checks and local SQLite/filesystem trust are not adversarially atomic. A simulated acceptance-claim note is still unverified; only the existing simulated invoice preview is exercised. No new dependencies, provisioning, paid services or Nexus Operative changes.
